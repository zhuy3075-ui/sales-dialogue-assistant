# 结构化二次蒸馏与方法论决策 Skill 正式规格

> 当前执行版本2.7.0：[技能入口](../SKILL.md)、[双方记忆](workspace-memory.md)、[综合谈单工作台](sales-workbench.md)与[中性判断](neutral-assessment.md)共同规定运行与验收。下文保留2.0起的方法/证据合同及历史实施记录；历史“本轮范围”“不自动安装”等不覆盖后续用户已给授权。原方法、来源、真实性和反例要求继续生效。

规格版本：2.0.0｜日期：2026-11-14｜依据：用户本轮明确要求。本文是实现验收合同；原始语料提供方法证据，软件规则与评测门槛是分析者设计，不能归为资料作者原话。

## 目标与问题

已知：上一版主稿约一万字，附录存有43方法、71模板、1063案例、5711证据。主稿压缩了条件、过程和例外，详版又按历次补充堆积，导致读者难以直接作决定。根问题是知识组织和调用机制，不是继续增加文章量。

本轮只重组已有已核材料，按需要回看上下文；不扩读188份未选材料、不恢复云端采集、不改原始文字、不自动全局安装、不发送实际业务消息。不存在新的真人成交实验结果。

## 层次与保存合同

1. **L1冻结资料层**：上一版约万字主稿、完整详版、原附录、旧Skill、结构化证据/案例/来源数据和登记可读原文/HTML，逐字节复制并建立SHA256清单。原文章节、标题、日期文字、上下文均不重排；附加索引放在L2。上一版主稿明确叫“上一轮蒸馏稿”，不冒称作者原文。原始PDF、图像、音视频仍在项目原路径，此文本快照不宣称包含所有二进制附件。冻结副本不得被渲染器覆盖。
2. **L2结构化方法层**：43张方法卡，保留全部方法而非只选12条。每张含问题、前置条件、执行步骤、具体案例、边界/例外、来源依据；每个陈述有证据编号及性质标签。记录作者观点与助理应用取舍差异。完整原规则、全证据链、原案例及反例记录继续可访问。
3. **L3决策与表达层**：从问题及已核事实选方法、组合步骤、处理冲突、提供候选方案；原71模板及风格参考继续使用，回复必须重新适配事实，禁止凭空移植价格、期限、成功经历。
4. **L4评价与演化层**：离线测试、盲评、人工反馈、业务结果分别存证；版本更新不回写L1，不把文本得分当业务效果。

## 方法卡数据合同

每卡必须具有稳定M编号、名称、维度、问题类型标签；六个核心栏目不得空缺。问题、每项前置条件、每个步骤、每项例外分别存`text / evidence / nature`。`nature`至少区分“分析者归纳”“分析者应用取舍”；原文引用另以精确quote显示。

来源记录必须保留E编号、来源编号、标题、原章节（缺失明确未知）、日期及日期依据、说话人及纠正依据、段落ID、原文件及行号或PDF页码、完整原段、相邻上下文、OCR核验状态。相邻段落只用于上下文，保留说话人，不能自动当作作者背书。时间未知不补造；收录时间不等于创作时间。

案例优先使用既有C编号，完整呈现背景、目标、动作/原话、结果、缺失信息及来源。没有适合的真实案例时，使用有来源的作者教学例，明确无真实执行结果；分析者新拟示例另标“模拟”。同一个客户跨日期要显式连接，不混合成多次独立验证。

“原文说过”的可信度与“方法有效”的证据等级分别标注。原有高/中/低归属结论不升级；方法卡操作化的细分步骤只是可试行建议，不能继承为高可信因果规则。正式引用沿用历史核验状态，本轮不声称重新目视所有OCR图像。

## 决策引擎合同

输入：问题原话、用户目标、关系/阶段、明确问题类型（可选）、已核事实、尚未确定项、已购权益、是否需要退款处理、联系偏好、交付能力、可用预算、价格/时间等约束。缺失保留unknown，不能以false代替。

执行顺序：

1. 识别一个或多个问题类型，说明识别依据；显式分类优先，关键词只作候选，无法匹配就返回待澄清。模型可作语义判断，但不得绕过硬约束。
2. 检查原有义务、明确拒绝、资金/能力、必须披露的信息。用户的有效事实与权益优先于营销策略；拒绝营销不取消原有售后责任。
3. 匹配有证据的方法，输出选择理由和前置条件缺口。相似分是检索优先级，不是成交概率。
4. 按“核事实→回应当前问题→可选下一步→验证/停止”组合少量方法；不是把43条一次性输出。
5. 比较冲突方法，展示双方来源、冲突类型、选择理由与被排除策略。无法解释的作者冲突保留，不强行统一，不以日期新旧自动裁决。
6. 至少在存在两个可行路径时提供A/B；分别说明目标、步骤、依据、适用条件、成本、风险、权衡、退出/验证条件。若缺事实只能条件成立后采用，则标条件候选；无第二可行策略时说明原因，不能为了凑B提供违规方案。
7. 输出待补事实与建议，不外部执行。模拟例不含臆造价格、日期、折扣、收益和客户结果。

实现边界：提供Python标准库可运行的确定性参考引擎，支持多类型匹配、硬约束、方法组合、冲突检查与候选输出；中文自由文本复杂隐喻、否定和上下文由Skill中的模型确认，不宣称关键词程序等于完整自然语言理解。冲突矩阵是精选决策规则，688条历史张力仍在附录；未编码张力须按上下文复核。

## 评估与迭代合同

每环节均必须列输入、输出、判定标准：结构/引文校验；匿名盲评；人工业务反馈；真实结果核验；变更提案；版本发布与回退建议。必须保留首稿和失败题，不反复改答案后宣称首次通过。缺真实业务数据时结果为未验证。

硬失败包括：编造事实/来源/承诺、忽略拒绝、剥夺已购权益、把相关当因果、把新拟当原话。硬失败不得被语气分或平均分抵消。人工反馈不自动成为真理，业务收益不覆盖退款、投诉、交付成本。所有阈值是项目选择的验收门槛，尚无经验校准，不标为作者科学公式。

## 方案取舍与实施顺序

推荐：冻结L1＋43方法卡＋可检查的本地参考引擎＋人工版本门禁。复杂度适中，字段/引用可验证，迁移仅增加文件与更新Skill入口；回退可取冻结副本，业务发布仍需用户。

更简单方案：仅方法卡和人工路由。成本低，但反复调用的约束、分支和方案差异难以一致核验。被拒方案：全库压成超长人格提示词或立即微调；来源难追溯、更新难局部验证、当前没有干净业务标签和充分效果证据。

失败模式：标签匹配过粗；案例貌似相关实为另一客户；条件归纳超出原话；主稿膨胀但决策仍不可用；盲评猜出版本；只记录成功单造成样本偏差。对应验证：字段级出处、明确未验证标签、边界分支测试、同条件候选对比、掩码随机化、记录全部入组分母及负面结果。

当真实反馈显示分类经常错误、候选无实际差异或无法支持业务目标时，先收窄/重写规则；当可靠业务数据证明现有路由不适用时推翻相应规则，不强行维护作者一致性。

P0：封存并验SHA → P1：43方法卡和源上下文 → P2：决策引擎与冲突规则 → P3：评估/反馈/版本机制 → P4：引用、保存、分支、包格式检查。每阶段更新PHASE_LOG和HANDOFF。
