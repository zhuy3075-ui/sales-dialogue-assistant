# 定制开发谈单工作流

版本2.4.0。适用：定制软件、数据监控、业务自动化项目。客户画像、谈前计划、方案审阅、报价异议与履约沟通都可用。用户不必知道阶段或卡号；助理负责按现有材料选场景。通用沟通继续用原规程，不把所有业务当软件项目。

## 从哪里进入

- “想做个系统”“帮我看看这个需求” → [DEV01—06](custom-development-scenes.md#dev01)：必要性、可行性、替代方案、多人决策、会前准备。
- “嫌贵”“AI做很快”“同行便宜”“免费试做”“说可以但没付款”“不回了” → [DEV07—12](custom-development-scenes.md#dev07)。
- “先少做一点”“要源码”“一直维护吗”“本地部署”“赶时间”“保证效果” → [DEV13—18](custom-development-scenes.md#dev13)。
- “顺手加一下”“尾款”“不好用”“不做了”“二期”“介绍客户分成” → [DEV19—24](custom-development-scenes.md#dev19)。

先读匹配卡的前提、边界和接话分支，不凭标题选择回复。每次主要用1—3张卡；跨问题先处理会改变当前动作的障碍。场景数据另有[JSON版](custom-development-scenes.json)，供宿主按DEV编号定位；旧knowledge.py不支持DEV，不向它发送新参数。原M/E/C仍用旧检索工具读取上下文。

## 先判当前任务，再决定怎么帮

1. **客户在买什么**：要解决的工作、使用人、输入数据、预期输出；“想要AI”不是已确认需求。
2. **现在卡在哪里**：需求未成立、能力未知、价值未确认、钱或采购流程、范围与责任不清、交付问题。报过价不等于前面已通过。
3. **当前约定是什么**：最新经双方确认的范围、价格、时间、交付、付款与联系边界。单方改口、转述和草稿不能自动覆盖旧约。
4. **这次能推进到哪一步**：弄清任务、确认验证范围、明确内部决定所需信息、确认范围或履约处理。不是每次都推动付款。

这些是助理内部核对项。已有信息直接用；没有就标未知，只补问一个会改变当前回复的问题。用户只想要一句话，就给一句话；“需要报告”才展开。没有任何信息时可以先问“你现在最想解决的是怎么回，还是明天怎么谈？”

## 业务事实不能从旧案例自动继承

既有一万元监控项目仅用于理解用户业务：多账号、每日数据、历史记录、可视化、源码和部署。金额、7—10天、IP费用、服务器配置、可获取字段是该次方案中的表述，不是通用报价或已验证能力，也不是所有新客户的背景。

每个新项目重新核对：当前方案、客户需求、访问和数据授权、真实可行性、团队资源、已有承诺。不可为了“懂用户”自动带入另一个客户的预算、名字或失败原因。

## 冲突与取舍

|同时出现的情况|先做什么|什么时候才换策略|
|---|---|---|
|客户说贵，又说用不上|先判断需求是否成立；明确暂不需要则暂停|对方愿继续且需求明确，才核价值/预算|
|愿意付款，但关键能力没验证|先说明不确定并确定可验证范围|验证结果支持、费用与责任说清后才确认开发|
|想尽快成交，但已有功能缺陷|先处理原义务|当前责任安排清楚后再讨论新需求|
|预算不够，也要求全部范围|区分付款时间与减项；核实际可行方案|双方接受真实条件才调整，不自动降价或延期收款|
|联系人积极，但合伙人反对|先尊重内部评估与联系人意愿|对方愿推动才提供内部说明；不越级联系|
|客户要立即上线，但依赖未齐|核依赖和团队排期，必要时讨论阶段演示|所有条件足以支持才给确定时间|
|客户沉默，但有待履约事项|营销停止与必要服务沟通分开|只为具体履约问题联系，不夹带促销|

规则来源：M01/M08/M10/M17/M18/M24/M30/M35/M36/M39/M40的业务组合；不是原文中的统一排序定理。原观点张力继续保留在方法卡，本表是助理应用约束。

## 给用户什么

**一句怎么回**：自然短句，通常1—3句；必要时附一行下一步。不要把检查表发给客户。

**客户画像**：说清“他已经明确什么、可能担心什么、还有什么不知道、谈的时候先注意什么”。业务角色、顾虑、决策关系都引用本次材料。提到老板不等于本人没权限；点赞或认可工具不等于采购承诺。

**会前小抄**：本次目标＋开场＋两个重点问题＋不同回应怎么接＋不能先答应的条件＋收尾。若需要A/B，写推荐路径与触发备选的事实；不能两条都默认成立。用户问“详细计划”再加准备材料、责任人、会后待确认事项。

**方案/报价审阅**：标明“原方案写了什么→客户可能怎么理解→缺什么→建议改句”。只查影响当前决定的内容：范围与不含项、前提、成本承担、验收、时间、源码与维护、付款安排。缺失不等于必然有错，不替用户补商业条款。旧方案中的错误承诺须明确纠正，不静默改写历史。

**完整谈单诊断**：还原时间线→判断具体卡点→指出原话的问题与可保留部分→给纠正话术和可选路径→下一步与停止条件→证据及缺口。不把未成交全归因于一句话；不把客户有预算当一定应买。

## 连续对话怎么用

每次收到客户新消息，更新事实而非反复套第一次话术。记录“此前建议、用户实际发了什么、客户真正回答什么”；没发过的建议不能进入已发生历史。客户如果纠正原假设，重新选择分支；先前的画像允许失效。

例如：觉得贵且愿聊 → 澄清是范围价值还是预算 → 若预算不足，核可行减项 → 若新范围不满足目标，就暂停；不能为了保单不断削价。具体接话在场景卡，每条结果都标未知。

用户要求“替我谈”默认拟稿或角色演练；不因此获得代发、签约、付款、折扣或资源操作权限。演练中扮演客户的发言是模拟，不写入真实客户画像。

## 将真实反馈转成更窄的经验

用户可说：“这句话好用”“客户看完还是拒绝”“后来成了”。沿用[反馈规程](sales-feedback.md)和[案例学习](case-learning.md)，先收原话、实际动作、结果和缺口；用户愿意再补关键条件。不要求用户自己填技术字段。

对应DEV编号、版本、适用条件可记录到旧工具支持的scenario/context文本，不给工具发未定义字段。私人案例留在Skill外；不自动把客户资料打入外发包。

“客户回复了”“确认范围”“签约”“收到款”“验收完成”“退款”分别记录。未核付款只保留用户自报；一次成功只够候选经验，不证明普遍有效。新增场景、业务判断和既有M/E来源要分层，真实反馈不能被写成资料作者原话。

## 覆盖边界

本版补充24张业务应用卡、48条回应分支和24条模拟反例。覆盖是设计层面的可调用路径，不等于通过真实客户验证。当前尤其缺少：不同规模开发项目的完整谈判到验收记录、多人决策的后续结果、真实变更/退款结果，以及未参与构建的独立测试样本。没有证据就保持未知，不用新增示例数冲抵这些缺口。

维护者可用[12组成对压力题](custom-development-evaluation.json)核对边界。实际运行时保留输入、原始输出、宿主与版本，再按事实、阶段/责任、策略、自然程度和下一步评分；目前输出与评分为空。已参与构建的题不能称为独立盲测，后续盲评另选真实未见材料。评分不代替付款、交付或业务效果证据。
